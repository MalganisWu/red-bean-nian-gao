# 决策：Agent 文件读取不加根目录限制

状态：已接受
日期：2026-09-17

背景：Runtime 提供两个文件读取实现。`createRootedReadTool(root)` 把读取限制在固定根目录内，
做目录穿越、符号链接和文件身份复检；`UnrestrictedReadTool` 不做路径限制，Runtime 的 README 明确
要求它「只能由已经提供进程级文件系统沙箱的宿主显式启用」。

产品一直注册的是无限制实现，但代码库内不存在任何进程级文件系统沙箱（`workspace` / `sandbox`
在 `backend/src` 中零命中），即实际处于「假设有沙箱但并没有」的状态。本轮评审提出该缺口后，
由产品负责人决定维持全盘可读。

选项：
- 补根目录沙箱（选定前的主要竞争方案）：每会话一个 `workspaces/<threadId>/` 目录，改用
  `createRootedReadTool`。安全性最好，但 Agent 无法读取工作目录之外的仓库、系统配置和依赖，
  代码与运维类任务会直接做不成，且需要为每会话定义目录生命周期。
- 维持无限制读取（选定）：Agent 可读取 backend 进程有权限的任何绝对路径。
- 不提供文件读取：能力缺口过大，不符合本平台「产品本身就是 Harness」的定位。

决策：维持无限制读取，不加根目录限制。

理由：本平台由部署者自持、面向单操作者，Agent 的可信级别与本地编码助手一致——用户明确表示
「如果不能帮我读全部的，有些事情你就没法做」。Runtime 把「是否限制路径」交给宿主决定的原意
正是让宿主按自己的信任模型选择，限制并非正确性要求。

后果：
- `UnrestrictedReadTool` 的注册是**有意的**，不是遗漏；`composition-root.ts` 在此注释说明，
  避免后续评审反复把它当作缺陷。
- 进程隔离、容器化或独立服务账号成为唯一的安全边界。**文件权限由部署方式决定，应用层不再兜底**：
  提示词注入一旦成功，可读范围等于 backend 进程的可读范围，其中包括 `backend/.env.local`
  所承载的数据库、Redis、MinIO、JWT 与模型凭据。
- 注册与授权仍然分离：该工具不进入 `DEFAULT_AGENT_TOOL_IDS`，是否可用由各 Agent 的
  `sys_tool_ids` 单独决定。默认 Agent 不获得文件读取权限。
- 若后续要收紧，应引入根目录沙箱并改用 `createRootedReadTool`，属于改变安全边界的产品决策，
  需重新评估而不是顺手修改。
