# 决策：切断定时任务的命令执行路径

状态：已接受
日期：2026-10-08

背景：[`2026-09-17-default-agent-shell-authorization.md`](2026-09-17-default-agent-shell-authorization.md)
把 `sys_shell` 授权给默认助手时，明确记下了一条未处理的后果——定时任务执行继承 Agent 的工具，只排除
交互类工具，因此**存在一条无人观察时执行任意命令的路径**。当时把它标注为「收紧安全边界，需重新评估
而不是顺手修改」，这份决策就是那次重新评估。

选项：
- 维持现状：定时任务也能执行命令，可运行「定期跑测试/巡检脚本」这类任务。
- 切断（选定）：把 `sys_shell` 加入 `EXCLUDED_TASK_TOOL_NAMES`，定时任务不再拥有命令执行能力。
- 收窄为白名单：允许定时任务执行固定的安全命令集合，需要新增一层命令准入机制。

决策：把 `sys_shell` 加入 `backend/src/modules/task/service/scheduling/task-execution-service.ts`
的 `EXCLUDED_TASK_TOOL_NAMES`。默认助手的授权不变，只有定时任务这条路径被切断。

理由：两条路径的可信级别不同。日常对话由操作者当场发起、当场阅读输出，命令的副作用落在人的观察范围
内；定时任务在无人观察时触发，输出要等到投递后才被看到，期间已经发生的事情没有中途拦截的机会。默认
助手的授权之所以可接受，前提正是「本平台由部署者自持、面向单操作者」——这个前提在无人观察的执行里
不成立。白名单方案能保留「定期跑脚本」的能力，但它需要设计命令准入机制，收益不足以支撑当前阶段的新
能力，因此不引入。

后果：
- **定时任务的工具集变为** `sys_ask_user`、`sys_scheduled_task_manage`、`sys_shell` 三者皆排除，
  即保留 `sys_get_time` 等无副作用工具，失去命令执行能力。
- **定时任务无法再运行构建、测试、脚本类任务。** 需要执行命令的场景必须由操作者在对话中当场发起。
- 安全边界只收紧不放松：`EXCLUDED_TASK_TOOL_NAMES` 是运行时过滤，对已存在的定时任务立即生效，无需
  数据迁移；已经创建的、依赖命令执行的定时任务会在下次运行时因缺少工具而无法完成。
- 这份决策取代 `2026-09-17-default-agent-shell-authorization.md` 中「存在无人值守的命令执行路径」
  一条；那份 ADR 的其余内容（默认助手授权本身、文件闸门降级、子进程继承宿主环境变量）仍然有效。
