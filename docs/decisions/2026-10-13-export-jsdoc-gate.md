# 决策：导出符号 JSDoc 门禁（档 C）与棘轮基线

状态：已接受
日期：2026-10-13

背景：两个仓都有注释规范，但没有一条把规范变成机械门禁。上一轮复查暴露两条缺口：产品仓的注释门禁
只扫 `src/modules/**`（`app/`、`infra/`、`platform/`、`shared/` 全在门外），且只检查类/接口**声明头**，
从不检查成员——而 `AGENTS.md` 早已写明「公开方法必须有职责注释」，这条义务从未被强制。

更根本的动机是行为性的：**AI 写的注释倾向于注释显而易见的东西，反而对复杂业务不描述**。要约束这个
行为，判据必须可机检。

实测证明 prose 不可机检：现有 JSDoc 里只有 38.9%（本仓）/ 40.8%（产品仓后端）点到了全部参数名，
但抽查「不合格」样本，它们恰恰是最好的注释——`runWithLlmRetry` 解释了「为什么只重试临时错误」与
「为什么这两个参数要注入」，`toRuntimeMessage` 解释了「不共享可变数组引用」的原因。**好 prose 故意
不点参数名**，任何基于名字的匹配都会把它们判成违规。所以选 `@param` / `@returns` 这种**形式**，
理由是可判定性，不是偏好。

实测存量违规（按「每个导出符号 + 每个公开成员」重算）：SDK 仓 481，产品仓 1183。构造函数整体豁免
（它既不是方法也不是访问器或属性，其依赖契约在组装入口更可读）。

选项：

- (a) 只做存在性门禁（有 JSDoc 块即可）：成本最低，但 `/** 关闭。 */` 也能通过，对原始动机零约束力。
- (b) 全量要求 `@param` / `@returns`，门禁立即生效 + 棘轮基线分批烧到 0（选定）。
- (c) 全量要求，但先补完再开门禁：一个上千处改动的巨型 diff，无法逐块评审。
- (d) 保持 prose 风格 + 机检「参数名是否被正文提及」：实测证明会把本仓最好的注释判成违规（见背景），
  且提及不等于说明。

决策：采用 (b)。

1. 规则：每个导出符号与每个公开成员（方法、访问器、公开属性）必须有 JSDoc 描述正文；
   函数与方法要求逐参数 `@param`，非 void 返回要求 `@returns`。`@returns` 仅在**显式标注了**
   且类型不是 void 类时要求（fail-open：没标注就不要求，否则门禁会顺带变成「先补返回类型标注」
   的连锁改造）。
2. 分层：判据是纯规则模块 `tooling/typescript/export-jsdoc-rules.mjs`（两仓逐字节相同，不 import
   `typescript`）；语法事实由各仓 `architecture-syntax.mjs` 的 `collectDocumentables()` 产出。
   之所以这样切：产品仓没有根 `package.json`，仓库根解析不到编译器 API。
3. 棘轮不是「存量豁免」：不在基线的违规失败（挡增长）；基线里有而现场没有的条目也失败
   （陈旧条目，让「烧到 0」成为机械强制）；`--update-baseline` **只能裁剪**，新增豁免必须手改 JSON，
   让它在 diff 里表现为 `+` 行。
4. 落点：两仓 `Makefile` 的 `ts-export-jsdoc-check`，同时进 `verify`（CI）与 `verify-quick`
   （pre-commit）。门禁是纯语法解析，不依赖构建产物。
5. 规范修订：`docs/standards/typescript-common-conventions.md` 明确 `@param` / `@returns` 是形式锚点、
   不受「不逐行复述」约束；并写明**门禁只管可机械判定的那一半**，复杂业务描述仍靠评审。

代价与已知问题：

- 会给约 40–60 个自明成员强制写上低信息量注释。这是档 C 的既定代价，由规范修订（门禁只管形式、
  业务解释仍靠评审）缓和，不消除。
- 前端 39 个 React 组件的参数从解构改为具名 `props` + 函数体首行解构：门禁要求参数是简单标识符
  才能写 `@param`。函数体其余部分不动，所以可读性损失限于一行。
- 规则层 fail-closed：遇到未识别的语法形态会直接失败，需要人工补进语法层。在本项目（单人 + AI 维护）
  这是有意的取舍——静默放行比报错危险得多。

后果：基线在烧到 0 之后删除，连同 `--update-baseline` 与 `--seed-baseline` 分支一起。
