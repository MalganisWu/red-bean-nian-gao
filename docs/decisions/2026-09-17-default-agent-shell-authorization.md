# 决策：默认助手获得命令执行权限

状态：已接受
日期：2026-09-17

背景：新增 Runtime 工具 `sys_shell` 后，产品需要决定它是否授权给默认助手。此前默认助手只有
`sys_get_time` / `sys_scheduled_task_manage` / `sys_ask_user`，全部是无副作用或纯交互工具；
`sys_shell` 是任意命令执行，属于新的能力等级。

选项：
- 保持只注册不授权（原状）：Agent 能读写文件但不能运行测试、构建、版本控制命令，「改代码并验证」
  这类任务只能改完就声称完成，没有执行证据。
- 授权给默认助手（选定）：日常对话即可执行命令。
- 授权给专用 Agent：边界最小，但用户需要切换 Agent 才能完成常见任务。

决策：把 `sys_shell` 加入 `bootstrap.ts` 的 `DEFAULT_AGENT_TOOL_IDS`，默认助手默认启用。

理由：不运行命令就验证不了改动，Agent 的价值会退化为「生成看起来对的代码」。本平台由部署者自持、
面向单操作者，可信级别与本地编码助手一致。授权必须落在 `bootstrap.ts` 而不是数据库——启动期会
把该常量并入 `core_agents.sys_tool_ids`，只改数据库会被并集覆盖。

后果：
- **默认助手可以直接执行任意命令**，包括安装依赖、发起网络请求、启动进程。
- **文件工具的「先读后写」闸门降级。** `sed -i`、`tee` 等不经过 `FileReadLedger`，该闸门在
  `sys_shell` 可用时只剩引导模型走正确路径的作用，不再是能强制执行的安全机制。依赖它作为安全
  机制的设计必须重新评估。
- **存在无人值守的命令执行路径**：定时任务执行继承 Agent 的工具，只排除交互类工具
  （`sys_ask_user`、`sys_scheduled_task_manage`），不排除危险工具。因此一个定时任务可以在无人
  观察时执行命令。若要切断该路径，需要把 `sys_shell` 加入 `EXCLUDED_TASK_TOOL_NAMES`，那属于
  收紧安全边界，需重新评估而不是顺手修改。
- **子进程继承宿主进程的完整环境变量**，包括 `backend/.env.local` 注入的数据库、Redis、MinIO、
  JWT 与模型凭据。凭据隔离依赖部署方式（独立服务账号、容器、密钥管理），不依赖应用层名单。
- 唯一的安全边界是进程隔离。若后续要收紧，应改为「默认不授权 + 显式白名单 + 沙箱」，属改变安全
  边界的产品决策。
