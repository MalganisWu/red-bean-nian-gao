# 决策：具名函数与中间件 dispatch（禁止用匿名闭包藏流程）

状态：已接受
日期：2026-10-13

背景：「包一层」这个动作在代码里没有名字——全藏在给 handler 重新赋值里。典型形态是循环里
`handler = (nextSignal) => current(info, next, nextSignal)` 层层替换（Runtime SDK 的
`runWithMiddleware`），读者无法指出哪一行在进入下一层、哪一行在开始执行。本仓同类形态有多行闭包
直接赋给字段（`context.eventSink = (event) => {…}`）、高阶函数工厂里藏流程、写得不明显的递归嵌套。
Koa 的 `dispatch(index)` 是同一件事的另一种写法，差别只在能不能顺着读。

实测规模（正则加括号配对的近似值，嵌套箭头会被外层吃掉因此只会更多）：体 ≥2 行的块体箭头函数，本仓
backend 76、frontend 121、design-system 47；SDK 仓 43。而真正的「赋值型藏流程」两仓合计仅 2 处。

选项：

- (a) 只做评审约定，不写机械门禁：成本最低，但这类写法会随新步骤悄悄长回来。
- (b) 按字面统一执行「多行即具名」并全量回填，容器嵌套另立条目（选定）。
- (c) 把判据收窄成「只有赋值型才算」：命中从 287 降到 2，改动最小，但规则对新代码失去约束力。
- (d) 为内联在调用点位置的回调（JSX 属性、路由注册参数）开豁免清单：等于规范第一版就给自己开约 268 张
  罚单的豁免，规则容易被无视。

决策：采用 (b)。

1. 通用规范新增「函数与流程可读性」章节：流程要能顺着读；箭头函数只在**同时**满足三条时使用
   （函数体只有一行、只使用一眼能看懂的外部变量、不承担流程控制）；多行 / 以后才调用并记住外部变量 /
   递归与中间件与重试与取消 / 回调里还有 `if`、循环或回调——一律具名。
2. 容器回调不套两层：`map` / `filter` / `some` / `find` 内再嵌容器调用时抽具名判断函数或改用 `for`。
   这条只写规范，不做机械门禁，存量不回填。
3. 中间件写具名 `dispatch(index, signal)`，下一跳放进有名字的 `runNext`；层与层之间的跳转必须有一行
   代码看得见。
4. 「先放进具名局部变量再传」的字段阈值从 6 统一到 4。
5. 通用规则抽出为跨仓共享件 `docs/standards/typescript-common-conventions.md`，与 Runtime SDK 仓
   逐字相同，本仓规范只留产品仓特有约束。

理由：本仓主要矛盾是「规则能不能被执行」，而不是「规则够不够细」。判据取「多行」而不是「是不是藏
流程」，是为了让它可机械检查、可被记住；(c) 的精确判据虽然改动小，但会让规则对新代码失去约束力——
而这类写法正是随新步骤长回来的。

后果：

- 通用件是共享的，两仓必须同步：改规则走「SDK 仓提交 → 本仓 bump `runtime.lock` 时因逐字比对失败而
  强制同步」，不再靠人记得改两边。
- 本轮**不做全量回填**：本仓 backend 76 / frontend 121 / design-system 47 处多行箭头函数保持现状，
  新代码遵守、触达即改；只修已明确定位、正是本规则所禁的个别实例。SDK 仓做全量回填。
- 前端 JSX 属性位置的多行回调，抽到组件体内用 `function` 声明，不用组件体内的 `const` 箭头
  （已写入 `frontend/docs/standards/coding-conventions.md`）。
- 内联在调用点位置的**单行**回调不受影响（如 `onChange={(e) => setValue(e.target.value)}`）。
- 容器嵌套的存量不回填，新代码遵守。
