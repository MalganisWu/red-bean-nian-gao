# 决策：报错说明一律中文，机器判断只看结构化字段

状态：已接受
日期：2026-10-15

背景：双仓共享规范已要求「面向用户或日志的错误消息使用简体中文；残留英文错误消息属于缺陷而非
风格偏好」，但两仓生产代码里仍有 **221 处纯英文报错说明**（SDK 91、产品仓 130）——从
`runtime/checkpoint/codec` 的校验（`checkpoint version must be a positive integer`）到
`platform/llm/registry` 的注册失败。原条款写在「注释」一节里，读起来更像只约束 JSDoc，没有覆盖到
报错说明本身。

Runtime 另有一处自我辩护：`RUNTIME_ERROR_MESSAGES` 的注释写着「文案刻意固定不变：日志与告警常按
文案做聚合，文案随版本漂移会让历史聚合规则失效」，并据此要求固定文案。

选项：

- (a) 保持英文，把「文案固定」当成契约：代价是中文这条工作语言约定在报错上不生效，且文案再也
  无法改进或本地化。
- (b) 全量中文化，机器判断改看结构化字段（选定）。
- (c) 只中文化「面向用户界面」的那一层、内部不变式保留英文：代价是边界难划——SDK 的内部校验错误
  同样会进宿主日志，而「会不会进日志」取决于宿主怎么用。

决策：采用 (b)。

理由：报错说明是**供人阅读的说明**，技术字段与值保留原文即可。把整句文本当成程序或告警的分类
依据，才会让文案无法改进。这条约束的正确解法是**换判据**（看 `code` 等结构化字段），而不是冻结
文案——后者是用一个更难维护的约束去换一个本不该存在的依赖。

后果：

- **范围**：两仓生产代码的全部纯英文报错说明，实测 221 处（SDK 91、产品仓 130，含极少数哨兵串，
  实现时逐条判断）。测试替身里的假错误串（`network error`、`blocked` 之类）不是报错说明，不改。
- **保留原文**：错误码、`sessionId` 一类技术标识、协议名、具体 ID 与数据值不翻译，例如
  `sessionId=xxx：会话重试失败`。
- **机器判断**：凡按 `message` 全文或子串判断、聚合的地方，改为看结构化字段。已知必须同步的：
  `RUNTIME_ERROR_MESSAGES` 的注释及其「文案固定」的理由；产品仓
  `runtime-delegation-runner.test.ts` 按英文文案的断言。
- **验收**：两仓生产代码不再有纯英文语义句；`RUNTIME_ERROR_CODES` 等稳定错误码保持不变；生产分支
  与告警分类不依赖消息文本；相关测试改为验证错误码或结构化字段。
- **代价**：宿主的告警规则若曾按英文文案匹配，升级后会失配——这正是要暴露的问题，而 `code` 一直
  在，迁移路径明确。SDK 尚未正式 semver 发布，故不构成破坏性升级。
- 共享规范里那条「错误消息使用简体中文」需同时明确**适用范围包含 SDK 的报错说明**，并写明技术
  标识不要求翻译；否则这条决策只在代码里成立、在规则里无据。
