# 开发流程 · 通用件

> 本文件是**跨仓共享件**，与 sibling 仓中的同名文件逐字相同，由 `scripts/check-shared-files.mjs` 校验。
> 本工作区特有的流程落点写在各自的 `SKILL.md` 与 `AGENTS.md` 里，本文件不重复。

## 一次开发的产出

三样，按「它回答什么」分：

| 目录 | 回答什么 | 时间性 | 读者 |
| --- | --- | --- | --- |
| `docs/plans/` | 这次要怎么做、做到哪了 | 执行中 | 执行中的自己 |
| `docs/decisions/` | 为什么是这条，不是那条 | 冻结、只追加 | 想改它的人 |
| `docs/design/` | 这套系统现在怎么运作 | 活的、随实现更新 | 所有后来者 |

没有第四样。需求不单独落盘：它由 decision 的「决策」「背景」两节承载（见下）。

> **「ADR」只在说格式时用**（`背景 / 选项 / 决策 / 理由 / 后果`），不用来泛指这批文档 ——
> 本仓的决策记录过半不是架构决策（风格、流程、安全授权都在里面）。

### 触发判据

三条判据都与改动大小无关：

- **plan**：需要人批准，或要分多批 / 有风险点 → 写。
- **decision**：**放弃了另一个可行选项** → 写。
- **design**：**当前事实变了** → 更新。

### 三条红线

每条挡住一种已经发生过的病：

| 谁 | 不许写 | 判据 |
| --- | --- | --- |
| decision | 执行状态与数字 | 这句话是「**决策时点的边界**」还是「**系统的当前事实**」？后者进 design |
| design | 进度与排期 | 这句话**在功能做完之后还成立吗**？出现「（首版）」「二期」「✅ / ⚠️ / ❌」即红灯 |
| plan | 现状 | 那是 design 的职责 |

`design` **可以**写「系统现在没有 X」和「为什么没有」——那是当前事实；**不可以**写「什么时候会有」
——那是排期。所以「已知缺口」这类小节是合法的，只要去掉「已确认暂不做」「首版只做 …」这类
时间限定词。

`decision` 与代码之间不直接相连 —— 代码注释只挂活文档（见通用件「注释 › 书写要求」）。

### 各自记什么

**decision** —— 必须写在动手之前。写在后面会退化成事后辩护。

```text
# 决策：<一句话>

状态：已接受
日期：<YYYY-MM-DD>

背景：  为什么要动（用户场景写在这里）
选项：  考虑过哪几条，各自的代价
决策：  采用哪一条
理由：  为什么是它
后果：
- **范围**：本轮做到哪、例外是什么、存量怎么处理    ← 这就是「怎么算做完了」
- **代价**：将来哪里会咬人、排除了什么
```

被取代时不改旧文件：在**新** decision 里写明它取代了旧决策的哪一条。

**plan**

```text
# 计划：<一句话>

## 要做什么      引 decision 的「决策」节；无 decision 时在这里写清
## 验收条件      见下一节
## 批次 / 进度
## 风险点与回滚点
```

**design** —— 写「现在是什么」：行为、数据流、边界、接口、依赖方向、验证入口。
不写进度、排期、批次编号。

### 验收条件写哪

| 情况 | 写哪 |
| --- | --- |
| 有 decision | decision 的「后果·范围」节 |
| 无 decision、有 plan | plan 的「验收条件」节 |
| 两者都没有（轻量档） | 交付报告，不落盘 |
| **可自动化的** | **测试** —— 上面三处只引用，不重述 |

**不要两处都写** —— 同一判据出现两份表述即是漂移源。

### 不落盘的

- **TDD 的红→绿证据、失败原因确认、TDD 豁免理由**：一次性的核验证据，写进交付报告即可。
  工具只能校验最终结果，不能证明测试编写顺序。
- 常驻检查表（发布就绪、目视确认、迁移演练等）不是「一次开发的产出」，它们待在
  `docs/guides/` 与 `docs/standards/`，由 plan 引用而不复制。

## 变更分级

| 级别 | 示例 | 前置产物 |
| --- | --- | --- |
| 轻量 | 文案、配置、内部重构、小型 bug | 写清验收条件与实施步骤，可在任务上下文；不建 plan |
| 标准 | 兼容性功能、非破坏性增强 | 简短计划；按复杂度决定是否落 `docs/plans/` |
| 架构/兼容性 | 新模块、公开接口变化、并发或持久化语义变化 | `docs/decisions/` + `docs/plans/`；破坏兼容性先取得授权 |

是否需要落盘由**风险与公共影响**决定，不以代码行数决定。交付后的 plan 冻结，不再承载当前行为说明。

## 六个阶段

| 阶段 | 产出 | 完成标准 |
| --- | --- | --- |
| 1 需求 | 验收条件 | 说清做什么、边界在哪、不做什么 |
| 2 计划 | 实施步骤；必要时落 `docs/plans/` | 技术方案 + 任务拆解 + 风险点 |
| 3 编码 | 代码 + 测试 | 行为变化先写会因缺少该行为而失败的测试，并确认失败原因正确 |
| 4 验证 | 全绿 | 最近风险的定向检查 → `make verify` |
| 5 文档 | design / standards / AGENTS | 每次必审；结论为「无需更新」也要写明理由 |
| 6 交付 | 交付说明 | 结果、测试先行证据或豁免理由、验证命令、文档影响、提交与同步状态 |

## 执行纪律

- 编写行为实现前先确定测试层级与验收条件；适用 TDD 时先运行失败测试并确认它因目标行为缺失而
  失败。符合豁免场景时，记录原因和替代验证。
- 先确定改动的真实来源与消费方；共享组件、契约或 token 不建立第二份实现。
- 只做用户授权范围内的修改。**提交、推送、合并、发布或其他外部写入仍需用户已有授权** ——
  完成本地实现与验证不等于自动获得这些权限。

## 文档影响审查

每次改动后查看完整 diff，从 `docs/README.md` 的活文档索引开始，沿相关链接逐份判断；判定表在各仓
`AGENTS.md` 的「文档影响门禁」。**每一类相关文档都必须得出「已更新」或「无需更新」的结论**，
不得用修改冻结记录代替同步当前事实。`make docs-check` 只验证索引与链接的机械事实，不能代替语义审查。

## 交付

- 先跑 `make docs-check`，再跑最近风险的定向检查与最终交付门禁；`docs-check` 通过不能替代上面的
  语义审查。
- 门禁全绿、`git diff --check` 干净、最终文件清单已复查，没有遗漏文档或混入无关改动。
- 文档影响已审查；无需更新项已写明理由。
- 最终报告：实现结果、测试先行证据（先失败后通过，或豁免理由）、验证结果、文档影响、提交与远端
  状态。**不要把「本地已修改」表述为「远端已更新」。**
